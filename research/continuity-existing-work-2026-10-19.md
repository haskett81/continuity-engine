# Continuity existing-work audit

Observed 19 October 2026. Research for **Which existing Continuity work is valuable, and how should its conflicts be reconciled?** This is a product recommendation, not implementation, a release approval, or proof of preparation savings. No module code, live world, original master, or campaign data was changed.

## Answer

Keep the existing repository and its free functions. Make the product's main job **recovering the unfinished business that matters for the next session from notes the GM already made**. Retain JournalEntryPage campaign records and small settings for configuration; retire the requirement to model every choice as a Decision with typed Consequences. The better third option is notes first, with optional linked Threads, Clocks, Knowledge and character beats when they help retrieval, and one authoritative home for each changing fact. This preserves D-013 while addressing the original continuity problem without requiring a second campaign database. [L1: D-008, D-013; L4: final recommendation; C1–C6]

The existing work is substantial enough to preserve, but it does not establish that the module saves total work, is ready for release, or has repeat users. The old paper exercise was completed and reviewed; its unproved result is lower total effort, not whether the exercise occurred. [L1: D-013; L3: Where we stand; L5: Kill test]

## Best-supported conflict resolutions

### Notes first, with optional structure at the point of usefulness

The old binary is misleading: rejecting mandatory Decision records does not require abandoning campaign consequences. D-013 already specifies ordinary notes, connected corrections/outcomes, optional active Threads and pressure Clocks, and no entry merely for unchanged state. The September review reached that conclusion after correcting an unfair comparison. [L1: D-013; L3; L4]

Choose that baseline and narrow the product promise to finding the relevant change, promise or loose end. Keep the six existing capabilities available, while allowing a GM to use notes without completing six categories. A prep view should point back to the canonical note/record; it should not require retyping it into another maintained list. Source-note anchoring, editing/correction and the smallest useful reminder belong in the later design decision, not a new mandatory causal schema in this audit. [L1: D-008, D-013; C2, C3]

Retire the legacy requirement that structured Decision/Promise objects are mandatory first-release features. D-009 addresses generic free-text fields on those proposed objects, but it also describes the Thread note log as the only free-text surface. That broader wording conflicts with the later ordinary-Session-note workflow; explicitly supersede it for Session capture under D-013 and the current resolution rather than claiming no conflict existed. Preserve its warning about duplicate or unused structure and D-008's capture-speed arbitration. Keep D-012 as archived design exploration rather than the default next build: a singular cause field cannot cheaply resolve all unknown outcomes, multiple causes and many outcomes; its original argument also overprices the alternative by treating Consequence as a separate document when the old spec calls it a typed child. [L1: D-008, D-009, D-012, D-013; L2: Information Architecture; L6: D-012 critique]

**Strongest attack:** ordinary notes may leave the GM rereading everything, while optional categories may still demand duplicate upkeep. That attack has not been defeated. A later scoped evaluation must compare correct retrieval and total setup/capture/correction/prep/upkeep against the GM's existing notes and a relevant current alternative. Do not re-run the completed paper exercise by default or claim estimated payback periods as measurements. [L1: D-013; L3; L5: Kill test]

### Keep native campaign documents; use settings for small configuration

Choose the existing JournalEntryPage store for campaign content, world settings for thresholds/schema version, and client settings for personal UI preferences. This is already the implementation's practical hybrid. Moving campaign content back into a settings blob would incur migration, link and export work while giving up existing document affordances; no measured storage benefit was found. [C1, C8, C10; L1: D-001, D-010]

The earlier rationale conflates a newly invented Document class with a supported module-provided subtype of JournalEntryPage. Foundry officially documents exactly this subtype pattern. It also warns that disabling the provider makes subtype documents invalid/hidden until reactivation, and suggests lighter flags/sheets or conversion where appropriate. Therefore the best version of retaining the store includes a documented, portable plain-note/export exit and safe migration checks—not a claim that native documents are permanent or automatically portable. For new ordinary notes, reuse native Text/Session notes where possible before inventing further subtypes. [Foundry module subtype guide](https://foundryvtt.com/article/module-sub-types/), [JournalEntryPage API v14](https://foundryvtt.com/api/v14/classes/foundry.documents.JournalEntryPage.html), [TypeDataModel API v14](https://foundryvtt.com/api/v14/classes/foundry.abstract.TypeDataModel.html)

Record a new explicit resolution superseding D-001 and disposing of D-010's pending status. Do not pretend the historical D-001 reversal condition was measured or satisfied by this audit. The current authorization to choose the better solution supports a new design resolution; it does not itself authorize migrating worlds. Preserve IDs, records and the append-only decision history. [L1: D-001, D-010; current planning request]

### One product authority, several supporting references

Use the decision register for accepted choices, PRODUCT_MASTER for the current scope consistent with those choices, and the sheet/presence specs for UI details within that scope. Treat code as evidence of implementation, not as automatic permission for everything it contains; treat harnesses and roadmaps as supporting designs/history. This reconciles the old two-spec problem without discarding useful UI work. The parent planning map should carry unresolved decisions until they are settled, then the maintained master should absorb the result. [L2: divergence warning; L6: Sources and their authority; L7]

### Protect the free core; choose companions from repeat-use evidence

The complete free core and additive separate paid companions are confirmed guardrails, now corroborated by BUSINESS_MASTER B-002. Existing export, player Chronicle, character view, factions and clocks cannot be removed or paywalled to create a paid product. The hub waits for two real useful modules. A large pack, a module-count target, an importer or a utility built merely to unlock the hub is not a product need. [L8: B-002; L12: phases 4.5–5; L13: free/paid map]

Keep shortlist ideas as candidates, not commitments. A Next Session Brief is closest to the present job, but it must improve on Board and ordinary notes without creating duplicate upkeep. Player recap submissions could be a genuinely additional companion; Clue Web, Module Doctor, calendars, downtime and importers each need separate scope and maintained-competitor checks. The old rankings are dated inputs; the original opportunity report's per-character knowledge and projected-clock claims are contradicted by the source. [L13; L14: claim table; C3–C6]

Retire arbitrary pricing, revenue ranges, creator-comparison conversion assumptions and Patreon-first wording from product requirements. The inspected documents contain conflicting suggestions; this public research note does not disclose private correspondence or select a commercial delivery route. Current route/policy evidence belongs in the private planning reconciliation. [L8: historical open rows; L12; L13: section 4]

### Preserve the bounded Jev feature and narrow its older spec

Carry forward the requested contract: GM button press; choose one reaction from a short GM-authored list; suggest hold/advance for a Clock; no model-authored displayed prose; every campaign change requires GM acceptance. Keep the helper optional and separate from the AI-free core. Separate computing a suggestion from applying it, and retain manual operation when it fails or is disabled. [current planning request; L9: sections 4, 6; L10: sections 4, 9–10]

Retire the old spec's default reaction ladder when a faction has no GM list. It contradicts the strict GM-authored-choice requirement. Abstain until the GM provides options; fixed interface states such as insufficient information can still be hand-authored. Start with a hold/advance recommendation, rather than assuming noisy multi-segment predictions add value. Confidence may help order suggestions, but must never bypass acceptance or be presented as established accuracy. [L10: sections 1, 3, 5; L9: spike and trust discussion]

The October fit report records nine calls on three synthetic situations and explicitly says this does not establish accuracy; latency was not measured. Its hosted relay, token costs, limits, provider/version pinning and upkeep estimates are historical proposals, not current operational facts. Preserve its useful input-minimization, timeout, offline and frozen-label/holdout design requirements, while leaving provider terms, rights, privacy, distribution and operating budget to current evidence. No Jev call occurred in this audit. [L9: sections 5, 8 and appendix A3; L10: sections 6–13]

The later honesty-check trial reports **no gain for that development task**: the combined workflow caught the planted false claims but required more helper effort; Jev alone incorrectly supported a privacy claim. It did not test the in-product reaction selector. The synthetic spike, development trial and future GM usefulness study must remain three separate proof states. Their raw files were catalogued; this audit did not independently rerun or regrade those experiments. [L11: Verdict, What was tested, Limits; L16]

## Recovery and deletion rule

First retire authority by adding a dated replacement pointer in the maintained index and preserving a recoverable baseline. Keep unique rationale, primary evidence, test inputs/outputs and accepted decisions. Only verified byte-identical/generated duplicates are potential deletion candidates, after comparison with the governing copy and recoverability check. Old prototypes and abandoned candidates generally belong in an archive because they explain why an option was rejected. No campaign record, released free function, Git history, hosted asset or original source is a deletion candidate merely because the new plan uses a simpler path.

## Coverage and remaining limits

This was a bounded catalog-and-source audit of the existing repository; product masters/NEED/decision records; selected platform bridge sections; the Continuity Cockpit specs, roadmap and HTML harness structure; the four-page root notes PDF; relevant September reconciliation/prep/market records; October path/poll/DMG/Jev reports and plans; and catalogs of the two Jev experiment folders. It is not a whole-library audit.

Skipped as unrelated: skill rebuild/source trees, Watch automation internals, general platform-stack entries beyond relevant headings, account/key setup scripts, unrelated assistant outputs, instruction backups and full state-snapshot history. Catalogued but not independently regraded: full raw Jev arm outputs/evidence archive, all underlying community pages, the original research report's entire external source list, and unavailable cross-chat attachments. HTML harnesses were inspected as source/design assets, not rendered as live Foundry UI. The PDF was read as extracted text, not visually audited for layout.

No production prototype, user recruitment, spending, model call, build, live Foundry operation, migration, source-master rewrite or deletion occurred. Current commercial/policy correspondence is handled privately by the main planning session; older file statements about unanswered questions or unsent drafts must not be treated as current delivery status. The next product decisions are the precise first workflow/release, support/integration policy and bounded helper proof plan; this ticket's inventory does not complete the whole build-ready plan.
